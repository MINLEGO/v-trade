# Live-first durable-state and clean-database contract

Status: approved by the owner on 2026-09-13. This specifies
`vtrade-kalshi-live-v1`; it does not change the running `vtrade-kalshi-v1`
implementation.

Decision ticket: [Define minimal durable state and the clean database baseline](https://github.com/MINLEGO/v-trade/issues/35).

Canonical resolution: [approved contract](https://github.com/MINLEGO/v-trade/issues/35#issuecomment-5653795625).
The issue resolution is authoritative. This file is its local working copy.

## Scope and baseline strategy

- Build a new migration chain beginning at `0001` for the new empty database. Do not
  run, copy, or mutate the ten `vtrade-kalshi-v1` migrations as a compatibility step.
- Preserve semantic financial, safety, idempotency, and reconciliation invariants;
  do not preserve legacy physical tables merely because they already exist.
- Facts and immutable revisions are authoritative. Current order and portfolio state
  are transactionally maintained projections and must be rebuildable from facts.
- Shared venue identity, catalogue, and observations are not duplicated per agent.
  Cycles, mutations, financial state, reconciliation, alerts, and pauses are scoped
  to their owning agent wherever applicable.
- PostgreSQL stores typed authority fields and compact redacted metadata. Large raw
  payloads live in content-addressed object storage and are referenced by metadata.
- No market freeze, resumable stage, deterministic replay, harness transcript, or
  compatibility alias belongs to this baseline.

## Storage conventions

- Primary identities are UUIDs generated by PostgreSQL. Times are `timestamptz` and
  monetary values are exact integer microdollars. Contract quantities use exact
  hundredths of a contract.
- The migration runner retains its checksum-protected `schema_migrations` ledger.
  The clean baseline explicitly enables `pgcrypto` for `gen_random_uuid()`.
- Identity, state, money, quantity, freshness, rank, timestamps, foreign keys, and
  queried fields use typed columns. `JSONB` is limited to non-queried watermarks,
  redacted trace detail, and accessory metadata.
- Immutable fact tables are insert/select-only to application roles. State-machine
  and projection updates use explicit guarded transitions. Retention deletion uses
  a separate audited maintenance role.
- Retained authorities and evidence use `ON DELETE RESTRICT`. Cascades are permitted
  only inside a purgeable unpublished or unreferenced catalogue generation.
- Missing, stale, contradictory, invalid, or unverifiable financial evidence never
  becomes a zero or permissive default.

## Logical clean baseline

The names below are canonical logical names for the new chain. Implementation may
split migrations by dependency, but must not add speculative tables.

### Experiment, agents, and memory

| Table | Minimal stored fields and constraints |
| --- | --- |
| `experiment_definitions` | identity, experience/version, status, configuration fingerprint, code version, creation time; unique version and fingerprint |
| `prompt_versions` | definition, name/version, immutable body, SHA-256, creation time; unique definition/name/version |
| `model_configs` | definition, label, provider/model slug, immutable typed configuration plus accessory `JSONB`, SHA-256; unique definition/label/version |
| `experiment_runs` | definition, label, status, start/end times; unique definition/label |
| `agents` | run, name, initial cash, current pause state/reason/time; unique run/name |
| `agent_runtime_schedules` | agent, interval, next occurrence time, enabled flag; one schedule per agent |
| `plans` | agent, plan type, current revision, active/archived state; unique active plan per agent/type where required |
| `plan_revisions` | plan, revision number, immutable content, cycle and tool-invocation provenance, creation time; unique plan/revision |
| `beliefs` | agent, stable belief key, current revision, active/archived state; unique agent/key |
| `belief_revisions` | belief, revision number, proposition, probability/confidence when supplied, immutable rationale, cycle and tool-invocation provenance, creation time; unique belief/revision |

Committed plan and belief revisions survive an abandoned cycle. Mutable parent rows
select the current revision but are not the historical authority.

### Venue identity, catalogue, and observations

| Table | Minimal stored fields and constraints |
| --- | --- |
| `series` | venue and exact opaque series reference; unique venue/reference |
| `events` | venue and exact opaque event reference, optional series; unique venue/reference |
| `markets` | venue and exact opaque market reference, optional event; ordinary-binary identity only; unique venue/reference |
| `catalogue_generations` | build identity; `building|published|failed`; claim owner/lease and fencing generation; scan start/completion/publication times; separate creation and metadata watermarks; row count, validation fingerprint and failure reason; cycles may reference only `published` generations |
| `catalogue_generation_markets` | generation, market, exact compact listing projection, per-row `observed_at` and optional `source_updated_at`, eligibility and stable discovery rank; unique generation/market and generation/rank where applicable |
| `market_observations` | market, immutable lifecycle and selected market/rules fields, `observed_at`, optional source update time, fingerprint, optional evidence bundle |
| `market_price_ranges` | market observation, ordinal, exact start/end/step microdollars; unique observation/ordinal with valid non-overlapping ranges |
| `order_book_observations` | market, immutable observation/source times, fingerprint, optional evidence bundle |
| `order_book_levels` | book observation, YES/NO, bid/ask, ordinal, exact price and quantity; unique observation/side/ordinal and price |
| `fee_policy_observations` | market, structural policy identity/version, observation/source times, fingerprint, optional evidence bundle; exact fee parameters and required evidence roles are owned downstream |
| `resolution_observations` | market, venue status, binary result when present, settlement time when present, blocked state/reason, observation/source times, fingerprint, optional evidence bundle |

The compact generation row contains the projection already approved by the live
catalogue contract: references, search text, lifecycle times/status, available
volume/open-interest/liquidity metrics, available indicative prices, capture time,
source update time, and generation identity. Missing optional values remain null.

A cycle references one published generation; generation membership is not copied for
the cycle. The tracked market set is a view over every market referenced by a
retained financial fact, including completed history. A narrower maintenance view
selects open order attempts, non-zero positions, unresolved reconciliation cases,
and unsettled records. Neither view is another mutable table.

A generation is invisible while `building`. Publishing is a single transaction that
validates completeness and row count, marks it `published`, and advances its creation
and metadata watermarks. Failure marks it `failed` without advancing either
watermark. Published rows and watermarks are immutable; all cycle and read paths
enforce `published` at the database boundary.

### Occurrences, cycles, invocations, and trace

| Table | Minimal stored fields and constraints |
| --- | --- |
| `cycle_occurrences` | agent, scheduled time, `schedule|operator` trigger, `pending|skipped|activated`, start-gate result/reason and claim lease; unique agent/scheduled time/trigger identity |
| `decision_cycles` | unique occurrence, agent, published catalogue generation, `running|completed|failed|abandoned`, activation/terminal times, lease owner/expiry, fencing generation, last durable boundary, redacted terminal reason; at most one running cycle per agent |
| `cycle_trace_events` | cycle, cycle fencing generation, monotonic sequence, event type/status, occurrence time, redacted detail `JSONB`, optional artifact and typed invocation/effect references; unique cycle/sequence |
| `provider_invocations` | controlled scope `cycle|catalogue|maintenance`, nullable cycle/generation/agent foreign keys with shape checks, applicable fencing generation, provider/operation, stable identity, `reserved|sent|completed|unknown`, request fingerprint, reserved and actual usage/cost fields when known, timestamps, redacted error/result metadata |
| `tool_invocations` | cycle, agent, cycle fencing generation, server-issued identity, tool name, argument fingerprint, `started|completed|failed|unknown`, timestamps, result fingerprint and redacted result/error metadata; unique identity and fail-closed divergent reuse |

Read tools need only trace events. A mutating tool requires a durable
`tool_invocations` row before its effect. Trace rows reference provider/tool/financial
records without duplicating their authoritative payloads. There are no resumable
stage checkpoints or replay records.

### Execution, accounting, risk, and settlement

| Table | Minimal stored fields and constraints |
| --- | --- |
| `execution_contexts` | immutable market, market/book/fee observation references, assembled time and fingerprint; all evidence must be causally valid and sufficiently fresh under the later execution contract |
| `risk_policy_versions` | immutable policy version, exact parameters and fingerprint, effective time |
| `risk_checks` | agent, execution context, risk policy version, exact typed inputs/outputs, `approved|rejected`, reason, checked time; immutable |
| `order_attempts` | agent, originating cycle/tool invocation and cycle fencing generation, idempotency key, request fingerprint and typed order request, `started|completed|unknown`, result `rejected|unfilled|partially_filled|filled` required exactly when completed, execution context/risk check, timestamps and redacted reason; unique agent/idempotency key and unique mutating invocation |
| `order_events` | order attempt, monotonic sequence, event type, timestamp and redacted detail; unique attempt/sequence; immutable |
| `fills` | order attempt, ordinal/provider identity, market/outcome/side, exact price, quantity and fee components, fill time; unique attempt/ordinal and provider identity when supplied; immutable |
| `funding_events` | agent, `initial_capital|operator_adjustment`, exact amount, idempotency key, optional operator-action provenance, occurrence time; unique agent/idempotency key and at most one initial-capital event per agent; immutable |
| `ledger_entries` | agent, event type/time, exactly one explicit `fill_id`, `settlement_id`, or `funding_event_id`; XOR foreign-key constraint and unique source; immutable |
| `ledger_postings` | ledger entry, typed account, optional market and checked YES/NO, exact `cash_micros` and `contract_units` with exactly one non-zero dimension; immutable |
| `portfolios` | agent, current cash, monotonically increasing version, update time; one row per agent; rebuildable projection |
| `positions` | agent, market, YES/NO, exact quantity, cost basis and attributable entry fees, portfolio version/update time; unique agent/market/outcome; rebuildable projection |
| `reconciliation_cases` | agent, typed subject reference, `REQUIRED|CONFLICT|RESOLVED`, opened/resolved times and redacted reason; unresolved cases block only that agent |
| `reconciliation_events` | reconciliation case, monotonic sequence, event type/time, evidence artifact and redacted detail; unique case/sequence; immutable |
| `settlements` | agent, market/checked YES/NO, validated resolution observation, exact quantity/payout/fees, settlement time, unique idempotency key; requires `FINALIZED`, binary result and `settlement_ts`; immutable |

An order attempt is inserted before execution. Reusing its agent-scoped idempotency
key with the same fingerprint returns the recorded result; divergent reuse fails
closed. Keys are retained for the life of the experiment. `unknown` remains reserved
until reconciliation and is never treated as absent.

Finalizing an executed order is one PostgreSQL transaction: order result, fills,
fees, balanced ledger entries/postings, positions, cash, and portfolio version all
commit or none do. Settlement and funding use the same atomic rule. Deferred
commit-time constraints require exactly one ledger entry per fill, settlement, and
funding event. They require cash postings to sum to zero and contract postings to
sum to zero per market/outcome. Business rejection is a completed result;
infrastructure uncertainty becomes `unknown`.

The unique initial-capital event for an agent must equal that agent's configured
initial cash. The event and initial portfolio projection are created in one bootstrap
transaction, preventing duplicate or configuration-divergent funding.

Every outcome-bearing table accepts only `YES|NO` and references a valid market. The
ordinary-binary invariant makes a separate two-row `outcomes` catalogue redundant.

### Artifacts and operator controls

| Table | Minimal stored fields and constraints |
| --- | --- |
| `artifacts` | SHA-256, byte length, URI, media/schema type, creation/registration/retention times, cleanup state; unique SHA-256 and URI; content is external |
| `evidence_bundles` | immutable bundle identity, fingerprint and creation time; owning observations or decisions reference the bundle through typed foreign keys |
| `evidence_bundle_artifacts` | evidence bundle, artifact, typed role; unique bundle/artifact/role |
| `alerts` | optional agent, type, severity, opened/resolved times, deduplication key and redacted detail; unique open deduplication key |
| `system_controls` | singleton global pause state, reason, version and update provenance |
| `operator_actions` | actor, action, typed target, idempotency key, request fingerprint, outcome, occurrence time and redacted metadata; unique actor/idempotency key; immutable |

Agent pause state lives on `agents`; the global emergency control lives in
`system_controls`. Every resume or control mutation creates an `operator_actions`
record. Referenced artifact retention follows its owning record. The maintenance
worker compares the object-store inventory with PostgreSQL metadata; an uploaded
object that remains unregistered or unreferenced becomes eligible for cleanup after
seven days.

## State transitions and concurrency

- Occurrences move only `pending -> skipped|activated`. A stale pending claim may be
  reclaimed because no decision cycle or agent effect has started.
- Catalogue generations move only `building -> published|failed`. A build lease may
  be shared by waiting occurrences, but only its current owner may write members or
  publish through compare-and-swap on the fencing generation. An expired build lease
  is atomically marked `failed` without advancing watermarks; pending occurrences
  re-evaluate their start gate and join or start a fresh build. The expired build is
  never resumed. Readers never see building or failed rows.
- Cycles move only `running -> completed|failed|abandoned`. Lease loss fences the old
  worker; the fencing generation increases on every new ownership grant.
- Provider invocations move `reserved -> sent -> completed`, with unresolved sent or
  abandoned reservations becoming `unknown`. Unknown usage consumes budget
  conservatively until an audited resolution.
- Tool invocations move `started -> completed|failed|unknown`. A business result,
  including an order rejection, is completed. Unknown mutations are reconciled with
  their original identity.
- A cycle-owned trace, invocation, or order-attempt insert succeeds only through a
  transactional guard matching the current lease owner and fencing generation.
  Network results are checked again before they can influence cycle state.
- Reconciliation cases move from `REQUIRED` to `RESOLVED`, or to `CONFLICT` when
  evidence disagrees; `CONFLICT` may move only to `RESOLVED` through an evidenced or
  audited operator decision.
- Resolving an unknown effect updates the original row: evidence of an effect records
  the recovered result, evidence of absence records a completed rejection/unfilled
  result, and contradictory evidence remains `CONFLICT`. Provider usage stays
  conservatively reserved while its invocation remains unknown.
- Unique constraints and conditional indexes enforce one running cycle per agent,
  one published identity per generation, permanent financial idempotency, and no
  duplicate fill or settlement.

## Minimal indexes

Create only indexes required by established access paths:

1. due pending occurrences and one running cycle per agent;
2. published catalogue generations by publication time;
3. generation members by stable rank plus approved search/filter columns;
4. observations by market and descending observation time;
5. provider and tool invocations by cycle and non-terminal status;
6. order attempts by `(agent_id, idempotency_key)` and unresolved status;
7. fills and settlements by agent and descending financial time;
8. positions by `(agent_id, market_id, outcome_side)`;
9. unresolved reconciliation cases by agent;
10. open alerts by deduplication key and artifacts by retention deadline.

Do not add speculative indexes. Add later indexes only from measured query plans.

## Retention and cleanup

| Data class | Retention |
| --- | --- |
| Financial facts, idempotency keys, configurations actually used, plan/belief provenance, and operator actions | life of the experiment |
| Compact cycle traces, occurrences, cycles, and completed provider/tool invocations | 12 months, unless referenced by a longer-lived record |
| Unreferenced catalogue generations and non-financial observations | 90 days; the current generation is never purged |
| Referenced observations and artifacts | inherit the longest retention of their owner |
| Orphan objects | seven-day grace period after upload/registration opportunity |

An application maintenance worker performs small bounded batches without `pg_cron`
or a new service. It deletes eligible database rows before their now-unreferenced
objects, records metrics and operator-visible failures, and never blocks cycles,
reconciliation, position tracking, or settlement.

## Required PostgreSQL evidence

Implementation acceptance must use a real PostgreSQL database and cover:

- clean migration application, checksum validation, and idempotent rerun;
- competing occurrence/cycle owners and fencing of the loser;
- crash before and after provider send and financial commit;
- permanent idempotency across process restart;
- terminal abandonment and absence of same-cycle replay;
- atomic catalogue publication and no watermark advance on failure;
- balanced cash/contract ledger, initial funding, mandatory ledger links,
  rebuildable portfolio, strict settlement, checked outcomes, and duplicate rejection;
- independent reconciliation and settlement while catalogue discovery is down;
- agent isolation for reconciliation blocks and pauses;
- retention protection for referenced evidence and safe orphan cleanup.

Offline unit tests remain useful but are not sufficient proof for these guarantees.

## Boundaries left to downstream decisions

- `Define live execution fees reconciliation and settlement` owns numerical
  freshness limits, exact fee/risk formula fields, detailed reconciliation evidence,
  and settlement polling behavior.
- `Define provider budgets and degraded operation` owns cost ceilings, timeout and
  retry policy, concurrency, quota accounting, and any resulting budget tables.
- `Define verification branch cutover and code removal` owns the physical migration
  files, deletion inventory verification, deployment gates, rollback, and release.

No product code, SQL migration, deployment, or tool-surface change is approved by
this contract.
